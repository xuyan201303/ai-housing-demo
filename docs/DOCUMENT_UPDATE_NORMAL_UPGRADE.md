# 通常環境の後続更新手順（本輪では未実行）

通常環境は `http://localhost:5173` / `127.0.0.1:8000`、通常 DB は `data/housing.db` です。Phase 2 第2輪は別 DB と `5176 / 8003`、第3輪の初回操作確認は新しい別 DB と `5177 / 8004` を使用します。この文書は更新方法の案内であり、通常 DB の参照・移行・起動・確認・公開を実行した記録ではありません。通常切り替えは未実行です。

## 前提

管理者が通常環境の切り替えを明示的に許可した後に行います。その承認は、停止・バックアップ・通常 DB の管理用テーブル追加・同版起動の範囲を含めて確認します。資料の用途確認、内容確認、公開、実 AI の有料呼び出しをまとめて承認されたものとは扱いません。営業中の新規接客を止め、既存の接客を終えてから Backend を停止してください。Backend と Frontend は同じ今回の版を同時に使います。旧 Frontend と新 Backend、またはその逆の組み合わせで公開操作を行わないでください。

SDK の入れ替え、依存パッケージの再インストール、モデル・音声設定の変更、`.env` の上書きは不要です。TEST DB を通常 DB にコピーしてはいけません。

## 手順

1. Backend 停止後、通常 DB とアップロード原ファイルを営業データとしてバックアップします。WAL が残っている場合は DB 本体・`-wal`・`-shm` を同一時点で保管し、原 DB を触る前に復旧手順を確認してください。稼働中の SQLite ファイルだけをコピーしないでください。
2. 今回の Backend / Frontend の組み合わせを配備します。起動時の `Store.init()` は新しい管理用テーブルを `CREATE TABLE IF NOT EXISTS` で追加します。既存の原ファイル、SDK raw / normalized、確認記録、公開スナップショットを一括書き換えしません。
3. 更新後の Backend を通常設定で起動し、資料数・現行公開版・資料用途・有効期限が切り替え前と一致することを、許可された通常 Admin/API の読み取りで確認します。秘密値をログや画面に出さないでください。互換性確認では R2 `knowledge_boundary_version=2`、`admin_publication_contract_version=1`、`admin_publication_schema_ready=true`、SDK バージョン、通常用 DB／アップロード先、Frontend の Backend 接続先が一致していることを確認します。
4. Frontend を同じ版で起動し、Admin のログイン、フォーム・保存済み下書きの表示、公開内容編集・プレビュー・履歴が動作することを確認します。Customer は物件未選択の一般相談から開始でき、資料公開版の番号を確認できることも照合します。この互換性確認だけで資料の確認や公開を行わないでください。不整合があれば切り替えを完了したものとせず、下記の復旧手順へ進みます。
5. 実際の更新が必要なときだけ、社員が下書き作成 → 原資料照合 → 改訂確認 → 公開プレビュー → 明示公開の順で操作します。

新規の管理用構造は `document_revisions`、`publication_drafts`、`publication_submissions` です。旧確認は、現在有効な承認との対応が証明できる場合にだけ改訂として関連付けます。欠けた承認を推測したり、用途や期限を自動補完しません。

バックアップと切り替えの承認が完了した後に限り、既存の通常起動方法を使用します。以下は説明用であり、本輪では実行していません。Backend の起動により上記のテーブル追加が実行されます。

```sh
cd /Users/kyoen/Projects/ai-housing-demo
backend/.venv/bin/python -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

別のターミナルで、同じコード版の Frontend を起動します。

```sh

npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

`/api/health` の `admin_publication_contract_version=1` と `admin_publication_schema_ready=true` を確認します。旧コードと新しい管理用テーブルの不一致がある場合は公開操作を進めないでください。通常資料の確認・公開は社員による別操作です。

異常があった場合は新規接客と公開操作を停止し、保存した営業データのバックアップと整合するコード版へ戻します。TEST DB に置き換える、履歴を消す、公開版番号を直接戻す等の対応はしません。

通常 Chrome Demo、実 AI が最新の承認・公開資料を読み取る最終連動、実マイク・スピーカーの受け入れは別途必要です。隔離 TEST provider の検証はそれらを代替しません。Phase 2 第3輪のブラウザー操作結果が技術 PASS でも、社員本人の評価・通常切り替え・正式な運用開始とは別です。
