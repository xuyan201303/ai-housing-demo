## 2. V1 工作清单

每项的验收先在隔离测试 DB/fixture 执行。正式资料接入、资料公开、付费 API、物理设备验收及部署应各自按确认后的范围执行，不使用现有 acceptance 脚本批量代替员工确认。

### D1｜真实资料接入：读取、字段整理、确认三层

- **代码证据**：`backend/app/services/document_sdk_adapter.py:18` 的 `parse`，`PROPERTY_KEYS`；`backend/app/services/documents.py:34/47/59` 的解析、确认与校验。
- **已有能力**：PDF 用公开 `extract_native_text`，保留完整 SDK raw，按页面生成 knowledge 引用；XLSX 用 `inspect_workbook/read_sheet`，保留单元格/公式证据。PDF 文件/页数/字符预算及 Excel 包/工作表/单元格预算有限。读取结果不会自动确认或公开。
- **实际缺口**：PDF 结构化物件字段依赖英文小写 `key:value`，续行拼接为自制版式服务；`knowledge_scope` 也依赖固定文字。Excel 金利识别要求同一行有 `bank`、`rate` 等英文表头，公式单元格不作为已确认事实。普通日文销售资料可能读到正文，却没有业务字段；不能把 SDK 读取成功说成客户资料自动整理成功。检测到 rates 后会清空整个 normalized knowledge，混合工作簿的其他内容需单独规划。
- **优先级**：V1 必须支持客户选定的有限资料类型及人工补录；任意版式自动理解、扫描 OCR、旧 XLS、CAD/图纸语义、所有加密/复杂排版的通用支持后续再做。这里是当前应用路径不支持，不能推断配布 SDK 的所有 API 均不支持。
- **最小方案**：保持 SDK Adapter 只负责读取；应用层增加少数明确命名的客户资料映射配置（页/表/标题/单元格及单位），输出字段候选、缺项和原位置。可从 raw 选择原文/单元格，也允许员工填未识别字段；人工输入标为员工录入，不装成 SDK 提取。缺价格、对象、单位、日期时保持待确认。新增解析能力只能经已配布 SDK 公开 API，当前不另写通用 PDF parser。
- **客户需提供**：脱敏但保持真实版式的物件表、设备表、公司说明、FAQ、贷款表及更新前后版本；正常/扫描/缺页/合并格/公式等样例；字段含义、单位、发布权限、可支持输入清单。
- **验收方法**：逐份对照客户原件：SDK raw、整理候选、人工确认分别记录；同一内容不同标题/单位不能静默错配；未识别内容保留并提示；图像 PDF/不支持格式明确失败而非空结果成功；公式与缓存值不自动成为业务事实。

### D2｜逐字段来源及人工变更追踪

- **代码证据**：`DocumentService.confirm/validate_review/publish`；当前 confirmation 记录 reviewed、note、时间及 raw SHA；publish 的 `field_references` 主要是文档级；管理员可输入 `reference.location`。
- **已有能力**：raw 和 normalized 不随 reviewed 编辑而改写；确认与发布分离；确认后不能直接编辑旧资料。
- **实际缺口**：缺确认者身份、确认草稿指纹、字段候选到来源片段的精确绑定、改值原因和人工输入标记。手填位置文字不是独立校验。`ReviewData` 的内部字典约束较宽，不等于所有业务字段均有强类型合同。
- **优先级**：V1 必须；多级审批和电子签章后续。
- **最小方案**：按当前字段建立确认表单/明确数据模型，保留 raw 区域；保存输入 SHA、SDK/API 版、整理规则版、来源页/表/单元格、候选/确认值及员工身份。确认仍由员工本人发起，保存 note 和草稿 SHA；禁止解析成功自动确认、自动勾选。界面已有 checked=false 和编辑后重置机制必须保留；不能把浏览器复选框本身当成后端的身份审计。
- **客户需提供**：哪些字段必须确认、谁能确认/公开、允许人工补录的范围及证据要求。
- **验收方法**：编辑、切资料或重新解析后不能沿用旧确认；修改 reviewed 后 raw 字节不变；可追溯每个改值；未确认不能公开；不因缺字段自动补一个猜测值。

### A1｜员工后台：从 JSON 到业务表单

- **代码证据**：`frontend/src/Admin.tsx` 的 Detail、propertyFields、reviewDraft、confirm；`schemas/domain.py` 的 ReviewData。
- **已有能力**：物件基础字段已有表单，raw/normalized 可分屏查看；范围、来源、日期、确认说明与人工勾选已有界面。
- **实际缺口**：设备、knowledge、FAQ 和 rates 仍主要编辑 JSON；一般员工难以维护数组、条件与引用。金利草案是整理建议，不是业务批准。当前确认数据无持久草稿，操作失败/刷新需恢复编辑内容。
- **优先级**：V1 必须；通用低代码表单后续。
- **最小方案**：先做固定 FAQ/金利/设备行编辑器及逐项错误提示，来源定位和日期可见；高级 JSON 仅保留诊断入口。草稿明确与确认/公开分离，保存时需校验当前文档和 raw SHA。不要一次建设全行业动态 schema。
- **客户需提供**：实际员工的操作步骤、常用字段和必须展示的贷款条件；一位业务验收负责人。
- **验收方法**：不懂 JSON 的员工能完成上传→校对→确认；无效日期、重复行、缺引用能定位到行；任何草稿都不被 AI 检索；人为确认仍必须明确执行。

### A2｜重复、替换、发布差异与遗漏预防

- **代码证据**：`DocumentService.upload:17` 每次产生 UUID 并保存 SHA，但不查询同内容；`publish:108` 仅拒绝重复 ID，创建选中文档的完整新快照；Admin selected 初始为空，versions 展示历史但没有专用差异预览。
- **已有能力**：公开版本不可变，事务避免半发布；冲突价格/号地等会拒绝；旧会话固定旧版。
- **实际缺口**：同内容可重复上传；缺 replace/supersedes 关系、物件资料包、更新摘要、撤下原因、发布前“本次移除哪些资料”预览。漏勾金利/设备会导致新版缺资料；已有状态机不等于有可用恢复流程。
- **优先级**：V1 必须；复杂审批流后续。
- **最小方案**：SHA 提示重复并允许明确选择“复用/有理由另存”；更新必须关联旧资料。员工从当前发布集合建立下一版草案，新增/替换/移除逐项可见，发布前显示影响与必需资料缺口；这不是自动业务确认。恢复通过新建版本重新引用合格资料，不能改旧版或恢复过期资料。
- **客户需提供**：同名/同内容更新规则、各类必需资料、撤售/售罄流程、谁可撤下与恢复。
- **验收方法**：只替换概要不会无提示丢金利；同内容不同名称可识别；旧版继续可审计；恢复会生成新版本且重验期限；新老价格不能混合。

### A3｜过期提醒与错误恢复

- **代码证据**：`publish` 检查有效期；`ToolService.execute` 对事实访问检查期限；`Admin.Detail` 给 error 状态显示解析按钮，但 `DocumentService.parse` 只接受 uploaded，静态可见重试入口不一致。
- **已有能力**：过期/未来資料在部分发布和 Tool 路径被拒绝；AppError 以业务错误返回。
- **实际缺口**：缺到期列表/负责人提醒；错误状态缺明确的重试或重新上传恢复入口；公开 snapshot 返回与 Tools 的有效性过滤并不统一。
- **优先级**：V1 必须；复杂通知渠道后续。
- **最小方案**：明确可重试/不可重试错误，失败历史保留，新 attempt 或重新上传不覆盖 raw；员工页提供过期/即将过期列表，先采用后台显著提醒。公开显示与 Tool 共用有效性规则。不要无限自动重试或把失败改成完成。
- **客户需提供**：提醒提前天数、负责人员、过期时停用哪些能力及紧急处理方法。
- **验收方法**：隔离重现 error→恢复，UI 与后端状态一致；过期资料不能经公开 JSON 绕过 Tool 继续使用；提醒不自动延长期限。

### P1｜住宅多物件与公司设置

- **代码证据**：`publish` 只有一个 property 字典；`context.py:12` 用 lot 作 property_id，`observe_customer:65` 从唯一 lot 提取数字；list_properties 最多列一件；`ai.py` 的 INSTRUCTIONS 存在 No.15 的提示示例；App 的 Brand 固定 SANZO。
- **已有能力**：物件未选择可一般咨询，明确选择后才取物件事实；general/company/property 范围分离；金额声明和选择可更新。
- **实际缺口**：无法表达多个项目、同号地跨项目、销售状态；公司名称、欢迎语、营业时间、联络/无人响应规则没有独立管理设置。存在住宅字段和样本提示，但不是所有功能都硬编码 No.15：后端实际已有显式选择防护。
- **优先级**：V1 必须支持客户实际物件规模和单公司设置；多租户、全行业 schema、微服务后续。
- **最小方案**：引入稳定内部物件 ID（不等于号地或文件 SHA）、项目/号地展示别名及发布资料归属；一份不可变版本包含多个物件及共通知识，旧单物件版本保留读取兼容。歧义别名要求客户选择。公司设置为单公司记录；对外营业/保证等事实仍需来源和人工批准，不能变成无来源提示词。
- **客户需提供**：项目/号地清单、公开与内部状态、同名规则、公司品牌/営業時間/保証/联络方式、负责人。
- **验收方法**：A/B 物件切换不混价格、设备、FAQ 或贷款条件；两个项目同 No.15 必须澄清；旧会话仍固定版本；无公司资料时不编造营业/保证；未选物件不强推单一物件。

### P2｜住宅领域与共通接客边界

- **代码证据**：context、mortgage、loan_selection、guardrails 是住宅规则；documents/store/sessions、Staff 状态和语音传输具有共通性。
- **已有能力**：服务模块已经分开，不必推倒重建。
- **实际缺口**：公共 Tools、品牌、提示词与住宅字段耦合；直接提取为全行业平台会先增加复杂度，无法替代当前业务缺口。
- **优先级**：V1 只做明确边界；第二家客户出现后再抽取复用能力。
- **最小方案**：仍用单 Backend；住宅的物件/贷款计算/风险方针留在领域服务，共通层只负责确认发布、会话、权限、请求流和语音传输。先复用现有类和显式接口，不建插件引擎、服务总线或微服务。
- **客户需提供**：首家公司具体交付范围；不得用未知行业需求扩大 V1。
- **验收方法**：现有住宅计算/商品明确确认和 Staff 方针不回退；配置变化不会绕过业务限制。

### AI1｜检索、会话条件与 Tool 权限

- **代码证据**：`ToolService.execute:31` 用字符串命中及二字片段打分、最多 8 hits；`get_consultation_context` 会直接供给有效范围的多个条目；`AiService._respond:62` 读取最近 24 条消息、最多 6 轮调用、max_output_tokens=1500；context.observe_customer 和 loan_selection 负责明确声明/选择。
- **已有能力**：Tool 读取会话固定版，未确认 raw 不进入检索；过期、物件选择和贷款金额/商品有后端校验；模型不能自行指定任意公开金利数值。
- **实际缺口**：检索并非向量 RAG 或经过客户问题集验收的日语语义搜索；整段资料与多个源一起提供，回答引用不等于每句结论有对应依据。预算/家庭需求/时间等条件没有统一显式结构；对象切换后需定义哪些条件继承、哪些重确认。Tool 业务分支有保护，但模型调用权限缺独立的明确 allowlist/参数统一验证边界，不能仅依赖请求中 function schema。
- **优先级**：V1 必须；向量检索/复杂 agent 后续，先证明现有检索能否满足资料规模。
- **最小方案**：对客户问题做固定检索回归，保留未命中“不明”；用有长度上限的段落/范围过滤，输出引用到命中片段，不能仅给宽泛文档链接。建立客户声明与公开事实分开的会话字段，更新/撤销/切换有记录。Tool 名称、参数、角色、当前会话状态在服务器共同验证，副作用幂等；不开放确认、发布、改 DB 等模型工具。
- **客户需提供**：常见问法、同义词、严禁承诺事项、咨询条件、对象切换与继承规则、合格回答样本（不是自动 expected）。
- **验收方法**：使用客户批准问题集，漏检/误命中/无来源回答分别统计；恶意资料指令不能改变权限；旧金额、模糊“是的”、未选物件、过期资料不得成功计算；来源与声明分开；切换物件不混用。

### AI2｜语音层可替换与业务一致性

- **代码证据**：`RealtimeService.connect/listen` 和 `frontend/src/useVoice.ts` 直接依赖 OpenAI SDP/DataChannel/sideband；文字/语音共用 ToolService、observe_customer、guardrails，但会话构造与调用循环各有实现；config 支持声线配置，默认 marin。
- **已有能力**：显式麦克风授权、服务端 Tool、字幕/音频状态、关闭/挂断与错误提示；VOICE_STYLE 统一每次 response 的要求。`test_realtime.py` 检查工具、重复事件、错误、挂断和日语指令存在。
- **实际缺口**：传输协议与业务协调耦合；文字有每轮金利 Tool 注入，语音依赖自身上下文与 Tool，不能默认完全一致。三个现有声音自然度未获用户认可；指令含日语或请求成功，都不证明发音/韵律/听感通过。历史文档的试听 WAITING/成功记录不能替代此次客户判断。
- **优先级**：虚拟角色 + 日语语音 AI 接客是 V1 的核心，语音为对外交付必要能力。自然度、真实麦克风/扬声器及多轮业务验收必须完成。文字仅用于开发验证和故障备用，不能替代完整 V1 交付。支持第二家语音厂商后续或另行批准，当前不更换。
- **最小方案**：先定义薄的 VoiceTransport 接口（连接、转写、输出、取消、关闭、错误和 usage），保留现有实现为第一个 Adapter；业务动作依旧经相同后端服务。显式决定语音切换文字时沿用当前咨询还是结束新开，不能静默丢失上下文。跨渠道用同一已确认声明/商品校验和事实引用。
- **客户需提供**：合格日语听感标准（语音已确定为 V1 必需）、声线偏好、现场设备/环境、录音许可、供应商/账号及试验预算；未确认前不试付费 API。
- **验收方法**：同一输入脚本文字/音声产生相同业务条件与 Tool 结果；ASR 错字/金额需澄清。客户在实际麦克风/扬声器上评估口音、停顿、数字、延迟、打断、串语种；声音/字幕对应核对。记录接口 PASS 与自然度 ACCEPTED 两个独立结果。

### O1｜轻量咨询成果与咨询请求

- **代码证据**：Store 保存 message/tool events，Admin 有会话历史；StaffService.call 仅保存理由、末次问题、物件名、版本和状态；没有摘要、联络/咨询请求模型或真实预约集成。
- **已有能力**：咨询与副作用有持久记录，Staff 呼叫不是仅前端动画。
- **实际缺口**：不能把完整聊天直接当员工可执行摘要；缺来访/回电请求、联系意愿、已知条件/未知项和下一动作。
- **优先级**：V1 必须提供轻量成果；完整 CRM、营销自动化、外部预约写入后续。
- **最小方案**：先从明确声明/已执行 Tool 生成可编辑摘要，关联事件及版本；AI 摘要只能是待确认派生稿。客户明确同意后登记请求（咨询/回电/希望到访时段），联系资料仅限内部显示。状态名称只能“请求已登记/员工处理中/已联系/取消”；没有真实预约系统或员工确认，不得说预约成功。
- **客户需提供**：摘要字段、联系渠道/同意文案、必填与可选个人资料、谁处理及营业规则。
- **验收方法**：不能把 AI 推测填成客户申报；无同意不提交；重复请求可识别；同意、修改、撤销可追溯；未接预约接口始终显示请求而非预约确定。

### O2｜Staff 归属与无人响应

- **代码证据**：`StaffService.call:19/transition:51` 用 BEGIN IMMEDIATE、active 呼叫去重，状态 pending→accepted→completed；`frontend/src/Staff.tsx` 2秒轮询。record 没有责任员工 ID，转移接口也未传 actor。
- **已有能力**：状态转移和事件同事务，有幂等和状态冲突保护。
- **实际缺口**：共享 staff 身份无法知道谁接受/完成；缺转派、无人响应计时、下班提示和接客结束后的处理责任。
- **优先级**：V1 必须；工单系统/复杂排班后续。
- **最小方案**：受付原子绑定 employee_id，记录动作/负责人；根据客户确认的营业/等待期限展示真实“尚未响应”，允许登记后续咨询请求，后台列出超时待办。初期可使用现有 Staff 页，不先接新通知平台。完成应有处理结果，不等于联系或预约一定成功。
- **客户需提供**：员工名单、谁可领取/转派、等待时间、营业时间及无人接听的兜底联络方式。
- **验收方法**：两员工同时领取只有一个成功，另一方看到真实负责人；超时不自动 accepted；接客结束仍留待办；客户看到安全状态，不看到内部处理笔记。

### S1｜顾客可见、内部资料及公共返回

- **代码证据**：`api/routes.py:39` 的无认证 `/property` 直接返回 store.latest；`SessionService.start/view` 返回 snapshot，view 还带完整 tool_events/staff_calls；`customer_snapshot` 控制未选物件，但仅过滤部分范围，不是统一公开 DTO/有效期过滤；publish 没有 audience/internal 标记。
- **已有能力**：admin/staff 路由有角色校验，未确认 raw 不给 AI；会话 token 校验且 view 去掉 token；浏览器没有服务端 API Key。
- **实际缺口**：发布全量字典直接暴露到客户端，新增内部字段会意外扩散；knowledge/rates 与工具参数/结果可能直接可见。company 是知识作用范围，不是“员工内部”权限。无内部资料独立可见性模型。此处是代码结构风险，本轮没有读正常资料，因此不宣称已证实真实机密泄漏。
- **优先级**：V1 必须、正式开放前阻塞；不是等到 SaaS 再做。
- **最小方案**：明确 CustomerProperty/CustomerSession/CustomerStaffCall 等允许字段 DTO，不对字典无差别透传；公开返回与 Tool 共用发布/有效期/选择规则。资料再独立标注 customer/internal 和允许用途，默认不因确认而可公开；内部资料不得进入顾客 API 或顾客 AI 上下文。公共来源 URL 也需校验可公开、允许协议；不把 filename 或管理员位置说明默认都视作可公开。
- **客户需提供**：公开/内部资料清单、可见字段、允许展示的来源名称/网址、禁止对客内容。
- **验收方法**：插入 internal_note、内部文档、Tool 原始参数等 sentinel，遍历公共 endpoint 与 AI 上下文均不可见；确认但未发布资料不可见；跨 session token 拒绝；过期/未选物件不绕过规则；真实客户公开数据不因修安全接口全部消失。

### S2｜员工账号与共用终端清理

- **代码证据**：routes.auth 仅 admin/staff 两个 Basic 账号，Protected 把凭据放 React 内存；SessionService token 存 DB，无 TTL/闲置到期；Customer end/pagehide 尝试结束，useVoice 停止 tracks/peer，但断网/浏览器崩溃后没有服务器闲置回收。
- **已有能力**：角色路径分离、常量时间密码比较、结束状态拒绝后续操作、前端没有 localStorage 持久保存会话凭据。
- **实际缺口**：无员工个人账号/撤权、登录限速、服务端注销与自动超时；Basic 必须依赖安全传输；“结束接客”/pagehide 不是共用终端充分隔离。失败关闭路径还需核对所有画面状态是否清空。
- **优先级**：V1 必须；企业 SSO 后续。
- **最小方案**：单公司员工表、密码哈希、角色和有过期/撤销的服务器登录会话；不自建多租户身份平台。顾客终端加明确“下一位/清除”与 idle timeout、服务器回收 active/Realtime；清理消息、字幕、输入、金额、资料展开和 token。部署采用 HTTPS，正式关闭不需要的调试 schema 端点；CORS 不当作身份认证。
- **客户需提供**：管理员/员工名单、权限、终端摆放方式、闲置时长、域名/HTTPS/网络部署账号。
- **验收方法**：员工离职撤权立即生效；过期登录拒绝；上一位信息不被下一位看到；离线/关闭页面后会话有界回收、上游语音能关；登录错误不泄露凭据。

### S3｜日志、音频、备份和异常运维

- **代码证据**：Store JSON 表包括 documents/versions/sessions/events/staff_calls/confirmations；SQLite WAL；config.project_path 只允许工程内保存；main 对异常返回脱敏业务错误；Realtime 状态/连接存本进程内存，关闭函数尝试上游 hangup。app/frontend 业务路径未见音频录制存储；voice_audition 是独立测试录音，不是正常接客录音政策。
- **已有能力**：本地持久数据、事务、脱敏错误、上传格式/大小/请求体边界、手工重连而非伪成功。
- **实际缺口**：聊天/Tool 记录持续增长，无保留/删除/权限政策；缺受控诊断 request_id；没有 DB+原件+发布版本+确认事件联合备份和真实恢复演练。进程重启后语音连接及 active 会话一致性尚需处理，单进程没有 HA。不能因代码没存 WAV 就断言上游服务不保留音频。
- **优先级**：V1 必须；HA/灾备平台后续。
- **最小方案**：明确本地文本/音频与服务商数据处理边界，默认不新增录音；需录音时另行取得同意和保留规则。日志仅保留脱敏错误码/request_id，支持有限分页与到期删除，确认/发布审计的保留由客户决定。用 SQLite 一致性备份方式配合输入文件 SHA 清单，离线恢复到独立目录验全链路；未授权不备份/迁移正常 DB。保留 SQLite 单进程可作小规模 V1，但上线前量测实际并发并定义重启恢复。
- **客户需提供**：保留期限、隐私/供应商审批、备份目标/权限、恢复时间与数据损失容忍、运行管理员。
- **验收方法**：在隔离副本恢复资料→确认→版本→会话→Staff 关联；日志无密码/Key/完整私密正文；磁盘写入/上游断连/重启/解析失败返回真实状态，不能说预约或回答已成功；若规模超出单进程实测范围再讨论数据库升级。

### S4｜使用量、费用和外部服务边界

- **代码证据**：文字每次最多 6 轮和 1500 output tokens，未见 usage 持久计量/预算；语音 tool_count 每轮限制 8，turns 只累加，没有时长或公司月预算；response.done 保存语音 usage，但没有费用/阈值处理；公开 /sessions 可创建会话。
- **已有能力**：单次工具循环有界，Key 不给浏览器，429/连接失败不自动切服务刷成功。
- **实际缺口**：循环有界不等于总费用有界；缺并发、会话时长、每日/月费用预算、调用前额度及匿名入口滥用限制。Realtime 失败挂断或重启仍需服务商费用对账。
- **优先级**：V1 必须；精细收费系统后续。
- **最小方案**：接入文字/语音用量记录，调用前检查明确预算/并发，进行中限制语音时长与 turn 数；到限停止新付费调用、明确引导文字的可用状态或 Staff，不能自动改收费服务。费用按批准的供应商计价版本/用量核算，不能在计划里编固定金额。公网入口加应用/网关限速；IP 不能作为顾客身份。
- **客户需提供**：服务账号归属、模型/语音预算、每日/月上限、并发上限、超额处理与费用负责人。
- **验收方法**：以 provider 测试替身验证超额前不会出网、重复事件不重复计费请求、长语音有界终止；usage 丢失标未知而非零费。真实付费费用对账另行批准后测试。

## 4. 推荐的首轮开发任务：公共 API 返回白名单

**已实施首轮：HOUSING_V1_PUBLIC_RESPONSE_BOUNDARY_R1。只做这一小批，不同时改导入器、账户、语音或多物件。**

范围：增加明确的顾客响应 DTO/序列化；应用到 `/api/property`、session start/view/end/property-selection 返回；Staff 呼叫响应仅保留顾客所需状态；审计 `tool_events` 对客输出，只给顾客所需安全结果与出处，不返回内部请求参数/运维信息。按已有会话、选择与有效期合同统一顾客视图。Admin/Staff 的授权内部视图保留完整必要信息。

本批不重写 snapshot 存储，不修改正常 DB、不重新发布；不新加字段映射、embedding、语音提供商或登录体系。DTO 默认只输出明确列入白名单的既有顾客字段，未知新增字段不透传。资料级 customer/internal 分类是下一批 S1 的必要工作：本批没有这项能力时，必须明确仍不能导入混合内部资料，不把 DTO 通过说成资料隔离全部完成。

首轮决定：不返回完整 knowledge/FAQ/rates 或原始 Tool 事件；使用明确顾客模型、命中片段、安全产品选项与展示事件。文件名与手填位置不公开；来源 URL 限制为已核对的明确公共页面。原始 scope_notes 不公开，必要业务限定以应用层公开说明保留。详见 [Customer API 合同](CUSTOMER_API_R1.md)。合法文本中的机密不能由字段白名单识别。

验收：用隔离 snapshot 的 internal_note sentinel 和新增未知字段验证公共端点都不透传；未确认/过期/未选物件的输出按现有合同处理；会话授权不回退；顾客资料/贷款/Staff 正常流程仍显示必要信息；员工内部接口不因 DTO 丢失审计信息。API/Frontend/相关业务测试及 build 通过，付费调用=0，正常 DB 操作=0。

首轮隔离验收记录见 [R1 验收](../evidence/public_response_boundary_r1/acceptance.md)。只验收了本批明确范围；未自动启动后续任务。后续总体验收仍是一家公司的真实资料和实际员工能完整操作、顾客得到有来源的解释及真实请求状态；不是“接口成功”“README 完成”或一次大型重构结束。
